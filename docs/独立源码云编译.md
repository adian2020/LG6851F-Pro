Release 附件；当前父仓库与另一公开 fork 也未找到可恢复的 Release。

本分支选用现有源码作独立实验重编：参考 prepare-public-build.sh、
build-vendor-public.py、vendor-build-part.py 及 V2.10 的实际修改材料，不执行

不承诺与 V2.10 字节相同、全部行为相同或已经完成硬件验收。

## 构建流程

1. 检出 cloud-build-lg6851f-pro，在区分大小写的 Ubuntu22.04 环境构建；
   使用仓库 feeds-snapshot，保存 .config 防止 feeds update 清除包选择。
2. 隔离 files 中的所有旧 .ko、旧 APK 数据库和会覆盖新包的 iwinfo/rpcd 库；
   原始输入只保留在构建私有目录，不能重新混入成品。
3. 先构建标准 tools/toolchain，准备6.18.44内核；采用 V2.10 的 HNAT/nf_nat
   源码。构建原生 OpenWrt，再按 coex/cmn/warp/wifi/hwifi 顺序重编厂商模块。
4. 把仓库保留的三个有界解析/PMKSA修复源码交给当前 Kbuild 编译。补齐缺失的
   ELF辅助工具；按作者记录的函数入口重定位和 APCLI 指令条件检查修改新模块，
   雷达索引在源码中修正。任何符号、布局或预期指令不符均停止，不能跳过校验。
5. 用完整 native hostapd 源码和当前交叉工具链重编，不把旧 hostapd 当新结果；
   CPU/LED/PPE模块使用当前头文件和 HNAT 的 Module.symvers。
6. 分别应用 B、A 槽文件差异，跳过旧槽位 APK 数据库；分别重新组装根目录，
   校验启动门禁、当前模块代码来源、内核版本及所需模块，再按原签名工具导出。
   每轮只取对应槽产物，不能把B运行层配给A boot。检查CONTROL、内部SHA256。
7. 固件附带当前构建专用软件源地址；四个索引经过当前公钥验签，再由独立发布
   job写入 cloud-build-lg6851f-pro-apk 数据分支，目录使用源码SHA+运行号+尝试号，
   不覆盖重编前的公钥和包。APK私钥只留在构建机器，不上传日志或成品。

## 使用与产物

源码推送自动触发此分支工作流，不需要修改 main 让 workflow_dispatch 注册。
Actions 开启后可在仓库 Actions 页面查看新工作流；手动触发是否显示取决于
GitHub 对默认分支中工作流的注册状态，分支 push 触发为主要入口。

成品 artifact：LG6851F-Pro-source-experimental-构建编号，包含 a/、b/ 两个目录、
对应签名网页包、boot/rootfs、模块检查结果、中文说明和总校验清单。构建失败
则只保留诊断，不上传或发布未通过检查的固件。首轮构建可能暴露作者明确未曾
完成干净全量编译的兼容问题，需按日志继续修复。

该流程不生成或恢复原作者 Windows 工具下载，不自动闪存、不重启设备，不把
离线模块/签名检查当成硬件加速、冷启动或跨设备验证。原有
adian2020/openwrt-mt6990-lg6851f:cloud-build 及其正在运行的构建保持独立。
